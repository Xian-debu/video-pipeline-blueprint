# The 3D scene layer

3D here is a **layer, not a separate renderer**: a `<ThreeCanvas>` composited inside the same
frame as the DOM, driven only by `useCurrentFrame()`. Nothing in this layer reads a clock, a random
number, or the network during a render.

Composition: `ThreeStage`, 900 frames at 30 fps, three 300-frame shots.

| Shot | Frames | What it proves |
| --- | --- | --- |
| A procedural | 0-300 | geometry can be a function of the frame number: 49 cubes, height `sin(frame/22 - phase)`, no asset file |
| B imported | 300-600 | an external `.glb` is normalised, re-shaded with design tokens, and lit by the same three-point rig |
| C composite | 600-900 | a transparent 3D canvas is a layer over 2D text, not a video pasted on top |

## Five primitives

| File | Exports | Notes |
| --- | --- | --- |
| `src/design/three/Canvas3D.tsx` | `Canvas3D`, `CameraPreset` (`wide`/`product`/`low`/`top`) | Wraps `ThreeCanvas`; `background={null}` makes the canvas transparent (`alpha: true`) so 2D layers below show through |
| `src/design/three/lighting.tsx` | `StudioLights`, `Ground` | Ambient + key + rim; `Ground` is a shadow-receiving plane at y=0 |
| `src/design/three/CameraRig.tsx` | `Dolly`, `Orbit`, `aim` | Both rigs return `null` and move the camera in an effect from the current frame; `Orbit` interpolates degrees, not radians |
| `src/design/three/Model.tsx` | `useGltf`, `prepare`, `Model` | Loads outside the canvas, normalises to a declared height, floors the bounding box at y=0, computes missing normals, applies a material preset, optional wireframe overlay |
| `src/design/three/materials.ts` | `MATERIAL`, `makeMaterial`, `PAL` | Four presets (`matte` 0.88 roughness, `satin` 0.42, `metal` 0.22, `glow`) — the same tokens the 2D layer uses |

## The constraint that shapes the whole layer

`@remotion/three` 4.0.536 renders with the R3F frameloop set to `never`: the canvas advances
exactly once per frame, from `useCurrentFrame()`, via `ManualFrameRenderer`'s effect
(`advance(performance.now()); onRendered()`). Anything that arrives *after* the canvas mounted —
a model that finished parsing, a texture — is never drawn. The result is a deterministic frame with
a ground plane and no model, which looks plausible enough that a coverage gate passes it (the empty
scene measured 12.20 % coverage on frame 450).

So the asset must exist before the canvas does:

```tsx
const gltf = useGltf("models/nailong_v3_15k.glb"); // delayRender + GLTFLoader, outside the canvas
if (!gltf) return <AbsoluteFill style={{ background: C.bg }} />;
return <Canvas3D>…</Canvas3D>;                    // mounted only once the scene graph is ready
```

Two consequences worth remembering:

- `useGltf` holds the frame with `delayRender` and releases it with `continueRender` after
  `setScene`. A `requestAnimationFrame` delay does **not** help (the frame hash stayed identical)
  and would violate the no-real-clock rule.
- Paths must go through `staticFile()`: the bundle serves `public/` under `<bundle>/public/`, so a
  bare `models/x.glb` requests `/models/x.glb` and 404s.

## Asset pipeline

The imported model is a carved voxel mesh from an offline reconstruction
(`/mnt/e/aigen_out/recon_ref/phase3/nailong_v2_15k.glb`, sha256 `21e84b5d9dc62438…`). It has no
`NORMAL` attribute and its surface carries the staircase of the voxel grid.

`scripts/assets/smooth_glb.mjs` is a dependency-free Taubin smoother over the GLB binary: it welds
vertices by position, runs λ/μ pairs (λ = 0.5, μ = -0.53, 10 iterations by default), restores
the largest bounding-box edge to its original length, and rewrites the `POSITION` accessor in
place — same buffer size, same topology, so the result is still watertight.

```bash
node scripts/assets/smooth_glb.mjs public/models/nailong_v2_15k.glb public/models/nailong_v3_15k.glb
```

Shipped asset (`public/models/nailong_v3_15k.glb`):

| Property | Value |
| --- | --- |
| Size | 262,396 B |
| Primitives / triangles | 1 / 14,532 |
| Vertices | 7,270 |
| Extent | 112.393 × 134.073 × 99.95 (model units; normalised to 2.0 at render) |
| Normals | absent → computed at load (`computeVertexNormals`) |
| Watertight | yes (0 boundary edges, 0 non-manifold edges) |
| sha256 | `6300bc2a4bf60fcf…` |

Deeper smoothing (80 or 300 iterations) moves the surface by less than 1 % of its extent and does
not remove the banding: the residual pattern is the *shading* of a low-poly surface with smoothed
vertex normals, not stair-steps in the geometry. Shot B therefore draws a wireframe overlay
(`wireframe`, 28 % opacity), which turns the mesh density into information instead of pretending
the surface is polished. A cleaner surface is an asset problem (higher-resolution recon or SDF
re-extraction), not a material setting.

## Gates

`scripts/qa/model_lint.mjs` — pure Node GLB parser, no three.js. Checks glTF 2.x, one
`POSITION` per primitive, triangle budget (`--max-tris`, default 400000), extent, and
`--watertight` (edge-pairing test). A missing `NORMAL` fails by default; `--allow=no-normals`
downgrades it to a printed `~ allowed:` line, because the runtime computes them.

```text
PASS public/models/nailong_v3_15k.glb  262,396 B · 1 prim / 14,532 tris · extent 112.393×134.073×99.95
     ~ allowed: 1/1 primitives have no NORMAL (facets, not surfaces) — allowed: runtime computeVertexNormals()
```

`scripts/qa/three_frame_lint.mjs` — bundles the project, renders the requested frames, decodes
them with ffmpeg to raw luma, and measures the share of pixels that differ from the border median.
Rules: `--min-coverage` (default 1.5 %, empty scene or camera pointed at nothing),
`--max-coverage` (default 96 %, camera inside the model), `--min-mean` (default 2, black frame),
and `--repeat` (renders twice and compares sha256 — the determinism check).

```text
PASS frame 150  coverage 14.59%  bg 18  mean 37.18  sha256 b8d4e3d3d6cb2a68
PASS frame 450  coverage 17.83%  bg 22  mean 38.00  sha256 11668ce1a95690af
PASS frame 750  coverage 4.37%   bg 25  mean 27.01  sha256 21cfd6594f98c6b9
three_frame_lint: PASS — 3 frame(s) (determinism checked)
```

Composition is deliberately **not** gated: an object bleeding off the edge is legal in a 3D shot,
and an earlier iteration of the gate that forbade it was wrong. Framing is a human check — the
stills are recorded below and in `docs/verify-report.md`. Frame 750's 4.37 % is the composite shot:
most of the frame is 2D gradient, and the model is a small object on the right by design.

## Post-processing: the grade and the depth of field

`Canvas3D` owns the whole colour pipeline, so no scene touches the renderer: it sets ACES tone
mapping explicitly (`gl.toneMapping = ACESFilmicToneMapping`, exposure `0.9` for the paper-white
plate) and `Stage` adds a lens vignette as a CSS overlay on the 3D layer only — text sits above it
and is never dimmed.

Depth of field is a second pass written by hand (`src/design/three/DepthOfField.tsx`), not
`@react-three/postprocessing`: one more dependency is one more determinism risk for one effect. The
pass renders the scene into a half-float target that carries a depth texture, then draws a single
full-screen quad that blurs by circle of confusion (12 golden-angle taps, weights fixed by
`(uv, depth, uniforms)` — no time, no random, no inter-frame accumulation).

Four facts had to be measured, not assumed:

- **A render target skips tone mapping.** `node_modules/three/src/renderers/webgl/WebGLPrograms.js`
  (r186, lines 177-183) applies `renderer.toneMapping` only when `currentRenderTarget === null` (or
  an XR target). The target therefore holds linear HDR, and the pass has to finish the picture —
  that is exactly what the stock `OutputPass` exists for.
- **A render target skips the sRGB encode too** (line 213 uses `ColorManagement.workingColorSpace`).
  So the quad reproduces three's ACES operator verbatim (`color *= exposure / 0.6`, `ACESInputMat`,
  `RRTAndODTFit`, `ACESOutputMat`) and then encodes sRGB itself.
- **The sRGB transfer must be an explicit branch.** `mix(lo, hi, step(vec3(0.0031308), c))` rendered
  ~5 % brighter and desaturated against the direct path (223/223/217 where the direct render has
  213/209/200); the ternary form matched pixel for pixel. The reason is not understood, which is why
  the parity check below exists.
- **The target's colour is premultiplied.** Blending `SRC_ALPHA` into a `clear(0,0,0,0)` target
  leaves premultiplied RGB, so the pass averages colour and alpha separately and divides at the end.
  The alpha itself must be divided by the number of taps *actually taken*: dividing by `TAPS + 1`
  when the radius was zero gave `alpha = 0.077`, and the browser then composited the premultiplied
  canvas as `bg * (1 - a)` over the plate, lifting the whole object by ~10/255.

Parity check (the pass is only worth having if it is transparent when unused): with `blur = 0` the
frame is `mean 56.03 / p99 209 / max 237`, identical to the direct render. Of 1.92 M pixels, 5,130
differ by more than 2, and 98.5 % of those sit where local contrast is above 4 (silhouette
antialiasing). Determinism holds with the pass on (`three_frame_lint --repeat` on frames 6915, 4067,
7786), and a 1080p still costs the same 2.8 s with or without it.

Focus is a **measured number**, not a world point, and the number is a *view depth* (camera
space `z`), not a distance. Both distinctions are load-bearing:

- `|camera − point|` is not `−view.z`. The two agree only on the optical axis; the further off-axis
  a subject sits, the more the Euclidean distance overstates its depth. Using it focuses *behind*
  the subject, and a rack between two off-axis subjects can move the wrong way. This shipped in the
  first render of the look pass and was caught in acceptance: every gear was 2–3 px soft, nothing
  was sharp, and the "rack" made the wheel *softer*.
- A gear is not a point. These are big discs tilted into frame, so one part spans several units of
  depth on screen — the m=3 wheel measures 14.9–17.3 across its own face. Focusing "at the part's
  origin" therefore puts the plane behind the surface you are actually looking at.

The method is to render one frame with the pass rewritten to output `vec3(viewDepth, uFocus, 0)`,
read the depth at the pixel you want sharp (divide out the CSS vignette, which multiplies both
channels), and type that number into the shot. A `Dolly` drifts the plane while it moves, so the
number is taken at the shot's midpoint and must be checked against the depth at both ends; the drift
is bounded by how far the rig travels (2.6 units for `contact`, ≈1 px at its `range`).

A film blurs where it has something to say, so two shots carry depth and nine deliberately do not:

| Shot | `focus` / `range` / `blur` | Why this one |
| --- | --- | --- |
| `backlash` | 9.0 / 4 / 6 | wide, static camera: mesh zone measures 8.5–9.1; the big wheel's rim walks away from the lens, so softening the far teeth keeps the eye on the gap |
| `contact` | 9.5 / 5 / 4 | dolly close-up: mesh zone measures 10.5 mid-shot, 8.0 at the end; a real macro lens drops the near rim first |

`module` was going to carry a rack focus — the shot that says "换模数就换中心距" has a second wheel
in it, and moving the focus to that wheel would have been the point rather than the caption. The
depth map says no: both wheels are tilted discs whose depth ranges overlap on screen (pair
11.4–16.0, m=3 wheel 14.9–17.3), so there is no near layer and far layer to pull between, and a rack
would only have defocused both. That is a composition note for the next film: **a rack needs two
subjects that are actually at different depths.**

## Known limits

- No animation mixer, no skinned meshes, no textures: the layer is for geometry and materials.
- Shadows come from `<Ground>` only; there is no contact shadow for objects off the floor.
- `useGltf` caches nothing across shots. Two shots that import the same file decode it twice; for a
  longer film, hoist the load above the sequences and pass the scene graph down.
- Wireframe overlay is a presentation decision for this asset, not a general default.

## How a full film uses this layer (`Gears`)

The three demos exercise one primitive each. `Gears` (`docs/gears.md`) uses all of them for
332 s, and is the reference for what "3D-first" actually costs:

- **Every scene mounts the canvas full-frame.** Text keeps a column by shifting the scene group in
  camera space (`<group position={[shift,0,0]}>`), never by insetting the DOM box — `ThreeCanvas`
  renders the composition's 1920×1080 camera whatever its parent is (K23).
- **Geometry is computed, not loaded.** `src/gears/profile.ts` turns `params.json` into tooth
  outlines; `geometry.ts` extrudes them. That is what makes `geometry_check.mjs` able to check the
  picture. Imported models are reserved for assets whose inside is not the subject (the plates and
  props demos).
- **A flat part needs its own light.** The three-point rig is built for volumes; a gear plate lit
  only by it reads as a silhouette. Each stage adds one front fill (`[1.2, 3.2, 9]`, intensity 2.2).
- **Curves are tubes.** `Line.linewidth` is ignored by WebGL, so the involute is a
  `TubeGeometry` of radius 2.4 mm.
- **Camera motion is a `Dolly`/`Crane`/`Orbit` component**, so a still at any frame is a pure function
  of that frame: the whole film re-renders deterministically (verified by `three_frame_lint --repeat`).
  A move is chosen for what it says, not for variety: `open` cranes down onto the pair ("put the
  camera on the bench"), `planetary` rises to show the ring enclosing the planets, `history` rises
  while tracking the other way to carry the change of scale.

Cost, measured: the 9,983-frame cut at 86.7 % weighted 3D rendered as 11 segments in about
4.5 minutes of wall clock on the reference machine (first segment finished 09:41:45, last 09:46:10
in the delivery run; a second, earlier run agreed). Two runs ≈ 37 fps of 1080p, which is what
matters for planning: the per-frame cost here is the DOM/Chromium pass, not the triangles.
